# MAIN и VRIK в прологе у погранпункта

Живая диагностика PID36080, DLL `20bc608db288b46418ae4a062f302a833b687fbfad689ac6a077439bc73f1fc3`,
исходный коммит `b0a600cc`. Пользователь стоял на улице, не у зеркала и не
в разговоре. Игра и OpenXR Simulator продолжали работать.

## Общая причина

MAIN был привязан к компоненту `0x1B126C23650` другой сущности
`0x1B126C228F0`, примерно в 24 м от текущего игрока. Имя компонента `camera`
совпадало с именем настоящей камеры, а обновления старого компонента продолжались.
Поэтому восстановление по остановившемуся счётчику не срабатывало, и фильтр
`g_patchFast` не пропускал настоящую камеру к классификатору.

Программная точка на сериализаторе `exe+127F58` показала фактический компонент
`0x1B122200110`. Его владелец `0x1B1216C4100` совпадает с текущим игроком.
Позиция и ориентация подтверждены через `GetPlayer():GetFPPCameraComponent()`.
Адреса относятся только к этому процессу.

Поворот HMD на 15° доходил до обоих привязанных компонентов, но итоговый MAIN
терял все 15°. VRCAM получал нужную ориентацию. В трёх интервалах наблюдения
MAIN не находил идентификатор позы ни разу, VRCAM находил его на каждом кадре.

Счётчик `g_VRIKFreshTotal` увеличивался до проверки камеры, поэтому его рост
не означал успешную запись костей. Кэш содержал 0 костей; native-пара оставалась
от прежнего владельца/поколения пространства и отвергалась при чтении.

## Проверка причины без перезапуска

Под программной точкой сериализатора изменены только указатели плагина
`g_camObjMain` и `g_patchFast.owner[0]` на проверенный компонент текущего игрока.
Код движка, позы костей, квестовые флаги и сохранения не менялись.

После перепривязки повторён поворот HMD на 15° и возврат:

- MAIN: ошибка поворота в удерживаемой позе 0° вместо 15°.
- VRCAM: около 0,0028° в асинхронном чтении.
- В обоих видах идентификаторы позы находились; пропусков за измеренные окна нет.
- Native-пара обновилась с текущим владельцем, кэш VRIK содержит 476 костей.
- Исходная поза HMD восстановлена, программные точки удалены, игра оставлена работающей.

Пользователь подтвердил после перепривязки: «Да, оба работают» (VRIK и MAIN).

Артефакты: `build/prologue-main-36080/addresses.json`,
`camera-probe-final.json`, `camera-probe-rebound.json` и соответствующие `.summary.json`.
Первый `camera-probe.json` не содержит финальные камеры: в диагностике первоначально
было неверное смещение `TelemetryData::finalRsi`; исправленное чтение использует +80.

## Постоянное исправление

Классификатор проверяет `IComponent::owner` против текущего `PlayerIdentity()`
и при сохранении привязки, и при выборе кандидата по имени. При смене игрока
`SetPlayer` очищает MAIN и отключает быстрый фильтр для повторного определения.
Путь публикации позы и VRCAM сохраняется.

Отдельно найдено смешение нумерации уровней сцен. SDK и живая игра используют
`Undefined=0`, `Tier1=1` ... `Tier5=5`; UI хранит индексы 1...4 для Tier2...Tier5.
При настройке 3, подписанной Tier4+, прежнее сравнение отключало VRIK уже на Tier3.
`ShouldSuspendVrik` переводит настройку в значение enum без изменения INI и подписей.
В начале диагностики наблюдался Tier3, позднее в той же сессии — Tier2.

Целевые проверки прошли: `roomscale_scene_suspend`, `roomscale_gameplay`,
`roomscale_body_sources`, `roomscale_native_camera_pair` (4/4).
Порог наклона в этой диагностике не менялся.

Живая перепривязка подтверждает причину и восстановление цепочки. Автоматическое
определение владельца из новой DLL требует загрузки новой сборки; во время
диагностики использовалась прежняя DLL с исправленными указателями.

Release-сборка завершилась успешно. Новая DLL:
`d4d1a81568e473f15629c5db14bf977c2a4505a8ece1cbc9363dd72628a6ed3e`,
`build/bin/red4ext/plugins/CyberpunkVR_Stereo/Release/CyberpunkVR_Stereo.dll`.
По прямой просьбе пользователя PID36080 закрыт через x64dbg, затем новая DLL
установлена через `scripts/deploy_plugin.ps1`. Заменена только DLL; INI и
калибровка сохранены. Игра автоматически не запускалась.

Резервная копия, журнал установки и соответствующие старый/новый PDB:
`build/roomscale-plugin-deploy-20260921-222515/`.
SHA256 INI: `2daa2823086c1983b9d69610f00aa108f7aa7e88e166983f3f1afc50e6d7e9f5`.
SHA256 калибровки: `d8b468963a5ab844d5c21619fb4098850fbc421c6756d383ab8ba21883158874`.
При следующем запуске нужно заново определить PID и символы и проверить
автоматическую привязку MAIN к владельцу текущего игрока.
