# TE6 highlight / testing2: разбор DLL

Проверено 26 сентября 2026. Здесь highlight означает **блики и яркие отражения
на зданиях/блестящих поверхностях**. UI-маркеры к этому исправлению не относятся.

## Что проверено

Скачаны официальные бинарные архивы TE5, TE6 highlight и TE6 testing2, проверены
SHA-256 из GitHub release API. DLL testing2 из пользовательской папки побайтно
совпала с DLL официального архива. Чужой установщик и DLL не запускались.

| Версия | Размер DLL | SHA-256 DLL |
|---|---:|---|
| TE5 | 2 587 648 | `bf699efb1fc6a30f3eb90945524cc136ffb42773c875225ba1e0744b0ae325d0` |
| TE6 highlight | 2 588 160 | `f40f1c1dad1146ae302fa0dac44ffc465adcc85271e321cc069e4d5d530385e2` |
| TE6 testing2 | 2 617 344 | `bc3a561f42580de0acdbb48239c5c2bf9bda427dbf526a6ce5c8ad9a06cbf945` |

`git ls-remote` подтвердил: оба TE6-тега и `TofuExpress` всё ещё указывают на
`a9c81bbbfb899f762c2663b552e1baf14ad9aed4`. Поэтому ZIP исходников под именем
highlight не содержит описанные ниже новые изменения DLL.

В [описании highlight](https://github.com/dabinn/cyberpunk-vr-port/releases/tag/v0.1.6-TE6-testing-highlight)

в нашей сборке в ходе данного разбора не проверялся.

IDA разобрала 4 152 / 4 154 / 4 230 функций соответственно. Сопоставлялись
структура функций, инструкции, строки, экспорты и значения настроек; ключевые
функции декомпилированы и сверены с потребителями в установленном EXE 2.31.
Готовая реконструкция логики: [te6-render-fixes-recovered.cpp](te6-render-fixes-recovered.cpp).
Это читаемый псевдокод, не восстановленный оригинальный исходник и не готовый
для прямого включения в сборку файл.

## 1. Highlight: отдельный кэш графа для VRCAM

Новый перехват `GraphCacheLookup`, EXE RVA **0x983C80**, DLL highlight RVA
**0x134A30**. В TE5 его нет. Регистрация содержит строку
`[cull] GraphCacheLookup sub_140983C80`.

После штатного `GraphContextPrepare` (**EXE 0x79ACA0**, DLL **0x134B90**)
сохраняются в TLS первый подготовленный view и его CName/key из `view+0x28`.
Если текущий view — VRCAM, хук lookup заменяет ключ:

```text
hash = FNV1a64(seed=0x9EDCB08A284EFDDF,
              bytesLE(originalHash,8) + bytesLE(vrcamNameHash,8))
```

MAIN сохраняет исходный ключ. В нативной функции проверены четыре записи кэша:
попадание определяется 64-битным hash и числом элементов. Новый salt разделяет
MAIN и VRCAM даже при одинаковом исходном hash.

**Вывод по механизму:** это исправление разделения кэша графа рендеринга между
глазами. Изменения яркости материала, roughness или формулы specular здесь нет.
Связь с конкретным визуальным дефектом соответствует сравнению релизов, но
изолированный A/B каждого из перечисленных изменений ещё не выполнен.

ABI: у нативного lookup **пять аргументов**. Hex-Rays сначала показал три в
обёртке; ассемблер сохраняет R9 и пятый аргумент в стеке через tail jump. При
переносе нельзя брать упрощённый трёхаргументный прототип из декомпилятора.

## 2. Highlight: AA/upscaler учитывается раньше

Изменён `Detour_FlagCompute`, **EXE 0x1D49540**, DLL highlight **0x13B630**.

При `CyberpunkVR_StreamlineHistoryFix != 0`:

1. Из MAIN запоминается режим `viewData+0xF94` и признак первого наблюдения.
2. Перед штатным вычислением флагов VRCAM временно получает этот режим MAIN.
3. После вычисления исходное значение VRCAM восстанавливается.
4. При дальнейшем копировании флагов MAIN сохраняется **собственный вычисленный
   бит 33** VRCAM (`0x200000000`).

Это существенно раньше уже имеющегося у нас присваивания в
`SetStreamlineConstants`: нативный `FlagCompute` действительно читает `+0xF94`
при выборе возможностей view. Поздняя запись не изменяет уже принятые решения
построителя графа. Бит 33 сохраняется именно из результата оригинального
вычисления, а не принудительно включается.

Ещё одна сопутствующая разница highlight: из resolver удалено старое условное
принудительное переиспользование post-color индекса (`DealiasPostColor`). Нельзя
приписывать весь результат одной новой строке; главные связанные изменения
кэша и FlagCompute следует проверять вместе и затем по отдельности.

## 3. Testing2: FogHistorySync

В уже существующий resolver **EXE 0x1F3D20** добавлен участок; DLL testing2 RVA
**0x150B70**. Он действует только при двух точных условиях:

- текущий node — `CRenderNode_VolumetricFog`, **EXE 0x61C3BC**;
- возврат из вызова resolver — **EXE 0x61D0C0**.

После штатного resolve MAIN сохраняет полученный физический handle. VRCAM
получает этот handle, если с момента MAIN прошло не больше двух соответствующих
вызовов и собственный handle отличается. Добавлен экспорт
`CyberpunkVR_DebugFogHistorySyncHits` и лог `[fog-history-sync]` первых восьми
подмен.

Проверен и потребитель: в рабочей функции **0x61C648** этот вызов относится к
логическому fog-ресурсу, запрошенному с ID **0x49471DDA**; далее он привязывается
как входной SRV к compute-проходу с shader key **0x5718E9A1**. Второй fog-ресурс
в этой функции запрашивается с ID **0x4948B5BA**. Имя `FogHistorySync` взято из
самой DLL; текстовое имя ресурса в EXE не восстановлено.

**Таким образом, найденный новый механизм testing2 — синхронизация входа fog/
его истории между глазами.** Это не новая реализация карт теней и не изменение
`LocalShadowReuse`. На изображении объёмное освещение/затенение может выглядеть
как различие теней; отнести именно этот участок ко всем заявленным автором
случаям без визуального A/B нельзя.

Что проверено дополнительно:

- начальные значения общих экспортированных настроек одинаковы во всех трёх DLL;
- helper `LocalShadowReuseMode` имеет одинаковые нормализованные инструкции в
  highlight (`0x150DC0`) и testing2 (`0x1560F0`);
- два проверенных пути каскадов — sample lending и cascade-node handling —
  совпадают по логике; различия декомпиляции сводятся к размещению статических
  данных и их меткам;
- игровые файлы highlight отличаются от TE5 только DLL. У testing2 дополнительно
  изменены три CET init.lua (Stereo/Holster/Weapon). Архивы, шейдерные файлы и
  пользовательские графические настройки в этих пакетах не менялись.

Отдельно в testing2 есть новый sRGB-to-linear проход перед OpenXR submit,
с shader-функцией по кусочной sRGB-кривой. Это отдельная цветовая поправка из
описания релиза, а не скрытая замена найденной синхронизации fog.

## Что отсутствует в нашей ветке и как переносить

Сравнение с рабочей веткой на базе `0cc06d12`:

| Найденный механизм | Наша реализация |
|---|---|
| Разделение GraphCacheLookup по VRCAM | Отсутствует |
| Временный MAIN AA mode до FlagCompute | Отсутствует; AA меняется позднее в Dlss.cpp |
| Сохранение собственного бита 33 при force flags | Отсутствует |
| Точная подмена fog handle в resolver | Отсутствует |

Для переноса есть конкретные границы: `CullVisibility.cpp`, `FrameGraph.cpp`,
`SyncStereo.cpp`. Замена всей чужой DLL не нужна и затёрла бы наши более новые
камеры, Framegen и HUD.

Кэш и ранний AA — первый кандидат для отдельного A/B. Fog-подмену нужно
адаптировать к текущей последовательности кадров: счётчик до двух вызовов
**не доказывает совпадения кадра**. В оригинале найденного участка нет проверки
frame/pose/origin generation, смены разрешения или загрузки. При VRCAM-first
последовательности условие допускает последний MAIN предыдущего цикла. Это
следует учитывать вместе с временем жизни GPU handle и зависимостями очередей.
Наш проверенный `LocalShadowReuse=0` к этому переносу отношения не имеет.

Для этого исследования производственный код не менялся и чужая DLL в игру не
ставилась. Предыдущая наша сборка с сюжетными исправлениями и cyberware осталась
установленной.

## Артефакты

`build/te6-binary-review-20260926/` содержит проверенные архивы и DLL, три базы
IDA, inventory/fingerprints, структурные сравнения, декомпиляцию с ассемблером
и соответствующие функции EXE. Ключевые файлы:

- `highlight-cache.json` — новый lookup, prepare и регистрация.
- `te5-relevant.json`, `highlight-relevant.json` — изменения FlagCompute/resolver.
- `testing2-relevant.json` — новая fog-подмена.
- `game-consumers.json`, `fog-body.json`, `fog-resource-contract.json` —
  проверка значения аргументов и потребителей в игре.
- `highlight-structural-diff.json`, `testing2-structural-diff.json` —
  сопоставление версий; изменения TLS/адресов не приравнивались к новым фиксам.
